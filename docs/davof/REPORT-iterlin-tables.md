## What the port check located (PCL0)

The first column of the PCL0 table below shows plicRDF reproducing the fork's gate table to 4 digits at all six states. The fork's gate numbers for ringSum and ringLinear are NOT the pass-0 normals on the exact state: rerunning the fork's own binary with a step of deltaT/1e9 gives the same norms to 4 digits (N 64 standard: ringSum abs(n-n_e) L1 1.7765e-2, ringLinear 9.3467e-4, as in the gate table), so the evaluated state is the state after the fork's step, whose face fractions are re-cut from the planes (davofFaceFractionSource sweepOnly), independent of the step size. The fork's log of the first reconstruction on the exact state prints for ringLinear (N 64 standard) `negative weight in 96, max |W (q - qbar).y| 1.5946311480675948` and (N 32 standard) `negative weight in 0 ... 0.99687603418181592`; the port's pass 0 prints the same counts and the same maxima to all 17 digits. The ringArea normals of leia equal a brute-force ring sum (cells sharing a point, 27 cells, interface cells only; no cell outside the interface set has an area vector) to 1e-14, and summing the area vectors of all ring cells instead changes no digit (experiment, not committed). The ringArea state after ONE corrector pass agrees with the gate's ringSum within 1.0 % (N 32 standard, borderline) and within 0.7 % at the other five states. The ringLinear gate values are not reproduced by any corrector pass of this application (not verified why; a possible reason is that the fork's sweep re-cuts a face from one plane while the corrector takes the mean of the two clips, which was not checked).
